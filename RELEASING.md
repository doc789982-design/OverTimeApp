# Как выпускать сборку OVERTIMETAB

Инструкция для того, кто сопровождает проект — человека или ИИ. Она
писана так, чтобы её хватило без всякой дополнительной памяти: просто
следуйте шагам. История сборок (что въехало в какую сборку) — в
BUILD_HISTORY.md, она генерируется из коммитов git.

## Из чего состоит релиз

**Релиз = два обязательных файла, оба собирает CI автоматически:**

| Файл | Кто скачивает | Зачем |
|---|---|---|
| `OVERTIMETAB_<версия>_<sha>.exe` | человек | Установщик: двойной клик → мастер установки. Устроен как «заглушка + этот же zip» |
| `OVERTIMETAB_<версия>_<sha>.zip` | установленная программа | Автообновление: программа ищет на релизе файл с `.zip` на конце и качает его |

**Убирать exe с релиза нельзя** (человеку нечего скачивать), **убирать
zip нельзя** (старым установленным программам нечем обновляться — они
физически не умеют читать релиз без zip). Публиковать релиз вручную
командой `gh release …` тоже не нужно — всё делает скрипт ниже, он сам
проверит оба файла и откажется работать, если чего-то нет.

## Шаги (по порядку)

1. **Код готов.** В `components/AppTheme.qml` поднимите `appBuild` до
   следующего номера (сборки непрерывные, никогда не сбрасываются) и,
   если начинается новая версия, поправьте `appSemver` и `appVersion`
   (правила — раздел «Схема версий» ниже). В `CHANGELOG.md` добавьте запись
   и обязательно пометьте её номером сборки: `<!--b:243-->` —
   без пометки окно «Что нового» её не покажет. Запись пишется по
   правилам из начала CHANGELOG.md: журнал для обычного пользователя —
   только новые функции и глобальные перемены, простым языком, без
   мелочей и внутреннего устройства. Публикатор проверяет стиль сам и
   откажется выпускать сборку с кривой записью.

2. **Коммит и пуш** рабочей ветки.

3. **Карта сборок.** `python3 tools/build_history.py --write --tag`,
   закоммитьте обновлённые `BUILD_HISTORY.md` и `CHANGELOG.md`
   («История сборок: N»). Публикатор откажется работать, если текущей
   сборки нет в карте.

4. **QA-батарея** — все тесты из `qa/` должны быть зелёными
   (переменные окружения песочницы — в шапке любого теста).

5. **Публикация.** `python3 tools/publish_release.py` — без аргументов:
   тег публикатор берёт из версии (`v` + `appVersion`, например
   `v2.0.0-beta.1`). Скрипт сам: создаст/обновит релиз, **дождётся
   сборки Windows**, **проверит, что на релизе есть и zip, и exe**
   с текущим sha, снимет старые ассеты. Если сборка сломалась или
   файлов нет — он упадёт с ошибкой, и релиз надо чинить, а не
   обходить проверку.

6. **version.json.** Впишите в `updates/version.json` поля:
   `version` — машинная строка-мост «2.0.0-<канал>.<N>» (счётчик = номер
   сборки; релиз без канала — просто «2.0.0»), `build` N,
   `display` — имя из `appVersion` («BETA.1»), `url` — **имя архива**
   `OVERTIMETAB_BETA.1_<sha7>.zip` (НЕ полный адрес — это правило
   проекта, адрес склеивается с хранилищем). Коммит «version.json: имя
   архива сборки N» и пуш.

7. **Заголовок и заметки релиза**: публикатор ставит их сам
   («OVERTIMETAB 2.0.0-beta.1 · сборка N»; заметки — весь CHANGELOG).
   Первая строка заметок должна подсказывать человеку качать **.exe**.

## Схема версий

В `components/AppTheme.qml` живут два поля:

- **`appVersion`** — имя для человека. Пока версии нет — просто «BETA.1»
  (потом «RC.1»). С релиза имя = версии: «1.0.0», «1.0.1», …
  Его показывают окна и тосты, его же берут имена файлов релиза
  (`OVERTIMETAB_BETA.1_<sha>.zip/.exe`) и установщик.
- **`appSemver`** — семвер, только механика: тег релиза (`v` + семвер),
  сравнение версий, машинная строка обновления.

Лестница (версия появится на релизе):

    BETA.1 (1.0.0-beta.1) → RC.1 (1.0.0-rc.1) → 1.0.0 → 1.0.1 → …
    → 1.6.0-alpha.1 → 1.6.0-beta.1 → 1.6.0-rc.1 → 1.6.0 → … → 2.0.0

- **Каналы по старшинству**: alpha < beta < rc < релиз (без канала).
  Ступени можно пропускать: бывает только альфа, или альфа и сразу
  RC — как решит сопровождающий.
- **Первый релиз — 1.0.0** (никакого 2.0.0). Дальше патчи (1.0.1,
  1.0.2…) и минорные (1.1.0, 1.6.0…); 2.0.0 — осознанное крупное
  изменение, когда-нибудь.
- **Сборка** (`appBuild`) — непрерывная и сквозная: 1, 2, 3, … без
  сбросов при любой смене версии. Именно сборка решает, новее ли
  обновление (внутри одной версии может быть много сборок).
- **Машинная строка-мост** (`app_update.scan_version`) — для самых
  старых клиентов, которые сравнивают версии строкой и не знают
  сборок: «2.0.0-<канал>.<сборка>», релизы — голое «2.0.0». Их
  исторические строки живут в ядре 2.0.0 — мост живёт там же; канал
  настоящий, счётчик = сборка, поэтому мост монотонен всегда (даже
  когда у следующей версии канал снова alpha). После первого
  обновления клиент современный (сравнивает сборки) и мост не нужен.
- **Тег** = `v` + семвер, свой у каждой версии. Сборки одной версии
  передвигают тег силой (публикатор делает это сам). Релизные теги
  (без канала) больше не двигаются — каждый релиз финален, правки
  идут следующим номером (1.0.1).
- **Старые сборки обновляются всегда**: современные клиенты сравнивают
  сборки; самые старые переходят по мосту. Проверяет
  `qa/test_version_scheme.py`.

## Почему так (кратко)

- Установщик — стандартный **Inno Setup** (`tools/overtimetab.iss`):
  привычные окна «Далее → папка → установка», как у любой программы.
  CI ставит Inno через chocolatey и собирает `iscc`-ом из той же папки
  `dist\OVERTIMETAB`, из которой делается zip, — программа в обоих
  файлах побайтово одна и та же.
- Установленная программа ищет на релизе файл с `.zip` на конце (это
  зашито во все выпущенные сборки), поэтому zip обязан остаться рядом
  с exe.
- При установке поверх прежней Inno помнит прежнюю папку; при
  удалении спрашивает, удалять ли данные сотрудников
  (`Документы\OverTimeTab`), — по умолчанию они остаются.

## Готовые проверки (qa/)

- `qa/test_release_gates.py` — воркфлоу собирает zip и exe, публикатор
  требует оба, RELEASING.md на месте. Если тест красный — кто-то
  сломал релизную цепочку, чините, а не удаляйте тест.
- `qa/test_changelog_style.py` — правила журнала описаны в шапке,
  все записи им соответствуют, нарушения ловятся, публикация блокируется.
- `qa/test_installer.py` — скрипт Inno Setup: ключевые директивы,
  источник файлов, вопрос про данные при удалении; проверяет также,
  что самописный мастер старых сборок не вернулся.
